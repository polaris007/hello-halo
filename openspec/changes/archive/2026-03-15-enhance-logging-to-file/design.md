## Context

当前Halo应用的日志系统存在以下现状：

**Server端** (`src/server/utils/logger.ts`)：
- 已有文件日志记录功能，但日志文件默认存储在用户home目录下（`~/.halo/logs/server.log`）
- 支持环境变量`HALO_DATA_DIR`自定义数据目录
- 日志同时输出到控制台和文件
- 支持日志级别：DEBUG、INFO、WARN、ERROR

**Client端** (`src/web/utils/logger.ts`)：
- 仅支持内存缓存日志（最多1000条）
- 不支持持久化文件存储
- 提供下载功能，但需要手动触发
- 同样支持控制台输出

**主要问题**：
1. 日志位置不符合需求：用户要求日志存储在应用启动目录的子目录下，而非用户home目录
2. Client端缺少文件日志：浏览器环境无法直接写文件，需要特殊处理
3. 缺少报文内容日志：API请求/响应和大模型交互的详细内容未记录
4. Server端日志位置配置不够灵活

## Goals / Non-Goals

**Goals:**
1. 修改server日志默认存储位置到应用启动目录的`logs/`子目录
2. 增强server日志配置灵活性，支持环境变量和配置项
3. 实现client端日志文件记录（通过API发送到server或浏览器存储API）
4. 添加HTTP API请求/响应报文日志记录
5. 添加大模型交互请求/响应日志记录
6. 保持向后兼容性，提供配置选项支持旧日志位置

**Non-Goals:**
1. 实现完整的日志管理系统（如日志查询界面）
2. 支持多种日志格式（如JSON、CSV等）
3. 实时日志流式传输
4. 日志分析和告警功能

## Decisions

### 决策1：Server日志存储位置策略

**方案**：默认使用`process.cwd() + '/logs'`作为日志目录，支持通过环境变量`HALO_LOG_DIR`覆盖。

**理由**：
- `process.cwd()`返回Node.js进程的当前工作目录，通常是应用启动目录
- 符合用户需求"放到当前应用启动后所在目录的某个子目录下"
- 环境变量提供灵活配置能力

**替代方案考虑**：
- 继续使用`~/.halo/logs/`：不符合用户需求
- 使用`__dirname`：表示源代码目录，不是运行目录
- 使用配置文件：增加复杂度，环境变量更简单

### 决策2：Client日志持久化方案

**方案**：采用混合方案：
1. 浏览器环境：使用`localStorage`或`IndexedDB`存储日志
2. 定期通过API发送到server保存到文件
3. 同时保留内存缓存机制

**理由**：
- 浏览器无法直接写入文件系统
- `localStorage`简单易用，但有存储限制（~5MB）
- API发送方案提供集中化日志收集

**替代方案考虑**：
- 仅用`localStorage`：存储空间有限
- 仅用API发送：离线时丢失日志
- Service Worker + Cache API：复杂度高

### 决策3：报文内容日志格式

**方案**：使用结构化JSON格式记录报文内容：

```json
{
  "timestamp": "2024-01-01T00:00:00.000Z",
  "type": "http_request|http_response|ai_request|ai_response",
  "direction": "inbound|outbound",
  "endpoint": "/api/v1/...",
  "method": "GET|POST|...",
  "headers": {...},
  "body": {...},
  "status": 200,
  "duration": 123
}
```

**理由**：
- JSON便于解析和分析
- 包含完整上下文信息
- 与现有日志格式兼容

**替代方案**：
- 纯文本格式：不易解析
- CSV格式：不适合嵌套数据

### 决策4：日志轮转策略

**方案**：按天轮转，保留最近7天日志。

**文件命名**：
- `server-YYYY-MM-DD.log`
- `client-YYYY-MM-DD.log`
- `api-YYYY-MM-DD.log`
- `ai-YYYY-MM-DD.log`

**理由**：
- 简单易实现
- 防止日志文件过大
- 按类别分离便于查找

**替代方案**：
- 按大小轮转：需要监控文件大小
- 无限期保留：磁盘空间问题

### 决策5：向后兼容性处理

**方案**：提供配置选项支持两种模式：
1. **新默认模式**：日志存储在`process.cwd() + '/logs'`
2. **兼容模式**：通过设置`HALO_LOG_DIR=~/.halo/logs`恢复旧行为

**理由**：
- 最小化对现有部署的影响
- 用户可以选择性迁移

## Risks / Trade-offs

### [风险] 日志位置变更导致现有监控失效
- **影响**：如果现有系统监控`~/.halo/logs/server.log`，变更后需要更新配置
- **缓解**：提供明确文档和配置选项支持恢复旧位置

### [风险] Client日志存储空间不足
- **影响**：`localStorage`有5MB限制，可能存满
- **缓解**：实现自动清理旧日志，优先保留错误日志

### [风险] 报文日志可能包含敏感信息
- **影响**：请求/响应体可能包含API密钥、用户数据等敏感信息
- **缓解**：
  - 提供配置选项过滤敏感字段
  - 默认不记录`Authorization`、`Cookie`等敏感头
  - 支持对特定字段进行脱敏

### [风险] 日志文件可能过大影响性能
- **影响**：大量日志写入可能影响应用性能
- **缓解**：
  - 实现异步日志写入
  - 提供日志级别控制
  - 按天轮转防止单个文件过大

### [风险] 浏览器存储可能被清除
- **影响**：用户清除浏览器数据会丢失client日志
- **缓解**：定期通过API发送到server持久化

## Migration Plan

### 阶段1：准备（预估：1小时）
1. 备份现有日志文件（如果存在）
2. 更新部署脚本和监控配置
3. 通知相关人员日志位置变更

### 阶段2：实施（预估：2-3小时）
1. 修改server日志配置
2. 实现client文件日志
3. 添加报文日志中间件
4. 添加AI交互日志

### 阶段3：验证（预估：1小时）
1. 测试各种日志场景
2. 验证日志文件位置和内容
3. 测试向后兼容性

### 阶段4：部署
1. 更新应用版本
2. 监控新日志系统运行情况
3. 根据反馈调整配置

### 回滚策略
如果新日志系统出现问题：
1. 临时方案：设置`HALO_LOG_DIR=~/.halo/logs`恢复旧位置
2. 完整回滚：回退到上一版本

## Open Questions

1. **Client日志发送频率**：实时发送还是定时批量发送？
   - 建议：每10秒或累积100条时批量发送

2. **敏感信息过滤规则**：需要定义哪些字段默认脱敏？
   - 建议：`password`、`token`、`secret`、`api_key`等字段

3. **日志保留策略**：默认保留多少天？可配置吗？
   - 建议：默认7天，可通过配置调整

4. **大日志文件处理**：是否压缩旧日志文件？
   - 建议：保留最近3天不压缩，超过3天压缩为.gz
