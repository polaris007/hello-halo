## Context

当前系统采用混合存储策略，API-Key 配置同时保存在 `llm-config.json` 文件和 SQLite 数据库中。这种设计导致以下问题：

1. **代码复杂度增加**：需要维护两套存储逻辑和同步机制
2. **数据一致性风险**：文件和数据库可能不同步，导致配置不一致
3. **冗余存储**：相同的配置信息存储在两个地方
4. **维护成本**：需要确保两个存储位置的配置保持同步

随着项目从 Electron 桌面应用改造为 B/S 架构的 Web 应用，简化配置管理变得更加重要。由于应用尚未上线，现在是进行架构优化的理想时机。

## Goals / Non-Goals

**Goals:**
- 将 API-Key 配置完全迁移到 `llm-config.json` 文件中
- 移除数据库中 API-Key 配置的存储和同步逻辑
- 简化配置读取逻辑，直接从文件获取 API-Key 配置
- 保持 OAuth 配置在数据库中的存储方式不变
- 确保 API 响应格式保持一致，不影响前端兼容性

**Non-Goals:**
- 不修改 OAuth 配置的存储方式
- 不影响现有的文件存储结构和格式
- 不引入新的外部依赖
- 不需要考虑数据迁移，因为应用尚未上线

## Decisions

### Decision 1: 存储策略调整

**选择**：API-Key 配置仅存储在 `llm-config.json` 文件中，数据库不再存储任何 API-Key 配置信息

**理由**：
- 简化架构，减少存储位置
- 消除数据一致性问题
- 提高配置管理的清晰度
- 符合文件存储的设计初衷

**替代方案**：
- 保持混合存储但加强同步机制 - 被否决，增加复杂度且仍存在一致性风险
- 完全迁移到数据库存储 - 被否决，不符合配置文件化管理的目标

### Decision 2: API 端点修改

**选择**：修改相关 API 端点，移除对 API-Key 配置的数据库操作

**理由**：
- 减少冗余操作
- 简化 API 实现逻辑
- 提高性能，减少数据库操作

**替代方案**：
- 保留数据库操作但仅作为备份 - 被否决，增加不必要的复杂度

### Decision 3: 读取逻辑优化

**选择**：修改 `mergeAISourcesWithFileConfig` 函数，直接从文件获取 API-Key 配置，与数据库中的 OAuth 配置合并

**理由**：
- 简化读取逻辑
- 提高性能
- 确保配置的一致性

**替代方案**：
- 创建新的读取函数 - 被否决，增加代码复杂度

### Decision 4: 启动逻辑调整

**选择**：移除启动时的数据库到文件的迁移逻辑，因为数据库不再存储 API-Key 配置

**理由**：
- 简化启动流程
- 减少不必要的操作
- 提高启动速度

**替代方案**：
- 保留迁移逻辑作为兼容性措施 - 被否决，应用尚未上线，不需要兼容性支持

## Risks / Trade-offs

### Risk 1: 配置读取性能

**风险**：从文件读取配置可能比从数据库读取慢，特别是当配置文件较大时

**缓解**：
- 保持现有的配置缓存机制
- 优化文件读取逻辑
- 确保配置文件的合理大小

### Risk 2: 文件权限问题

**风险**：应用可能没有文件写入权限，导致配置无法保存

**缓解**：
- 保持现有的错误处理机制
- 提供清晰的错误提示
- 确保配置目录的适当权限

### Risk 3: 配置文件损坏

**风险**：配置文件可能被意外修改或损坏，导致配置丢失

**缓解**：
- 保持现有的配置文件备份机制
- 实现配置文件验证
- 提供配置恢复机制

### Risk 4: 向后兼容性

**风险**：修改后的代码可能与现有的前端代码不兼容

**缓解**：
- 确保 API 响应格式保持一致
- 进行充分的测试
- 保持 OAuth 配置的存储方式不变

## Migration Plan

由于应用尚未上线，不需要复杂的迁移计划。实现步骤如下：

1. **修改 API 端点**：
   - `POST /api/v1/ai-sources/sources` - 移除 API-Key 源的数据库存储
   - `PUT /api/v1/ai-sources/sources/:id` - 移除 API-Key 源的数据库更新
   - `DELETE /api/v1/ai-sources/sources/:id` - 移除 API-Key 源的数据库删除

2. **优化读取逻辑**：
   - 修改 `mergeAISourcesWithFileConfig` 函数，直接从文件获取 API-Key 配置
   - 确保与 OAuth 配置的正确合并

3. **调整启动逻辑**：
   - 移除启动时的数据库到文件的迁移逻辑

4. **测试验证**：
   - 测试 API-Key 配置的添加、更新、删除操作
   - 测试配置读取功能
   - 测试 OAuth 配置的正常运行
   - 测试前端兼容性
