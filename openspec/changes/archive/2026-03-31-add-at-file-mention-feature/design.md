## 背景

Halo 是一个基于 Web 的 AI 编码助手应用程序，已从 Electron 桌面应用迁移到 B/S 架构。该应用程序目前缺乏用户在聊天对话中轻松引用项目文件的能力。@ 文件提及功能将使用户能够快速准确地引用文件，而无需手动输入完整路径，从而提高生产力并减少错误。

## 目标 / 非目标

**目标：**
- 实现后端 API 端点以列出空间内的工件（文件和文件夹）
- 在聊天输入区域创建前端 @ 提及功能
- 支持文件搜索和过滤，以实现高效查找
- 启用键盘导航和鼠标交互进行文件选择
- 实现文件拖放功能，以实现快速引用
- 通过缓存机制优化性能
- 在不同浏览器中保持一致的用户体验

**非目标：**
- 修改现有文件系统结构
- 添加文件编辑功能
- 实现文件预览功能
- 支持网络文件系统

## 决策

### 1. 后端 API 设计

**决策：** 添加新的 API 端点 `/api/v1/spaces/{spaceId}/artifacts` 以列出空间工件

**理由：**
- 遵循 RESTful API 设计原则
- 与现有的基于空间的架构集成
- 支持深度参数以控制扫描
- 启用缓存以提高性能

**考虑的替代方案：**
- 重用现有文件系统 API：由于缺乏空间特定的过滤和缓存而被拒绝

### 2. 缓存策略

**决策：** 实现带有文件系统事件监控的服务器端内存缓存

**理由：**
- 减少频繁的文件系统扫描
- 改善 API 响应时间
- 保持与实时文件更改的一致性
- 对于典型项目大小而言内存效率高

**考虑的替代方案：**
- 数据库缓存：由于增加的复杂性和潜在的性能开销而被拒绝

### 3. 前端实现

**决策：** 扩展现有 InputArea 组件，添加 @ 提及功能

**理由：**
- 重用现有的输入基础设施
- 保持一致的 UI 设计
- 最小化代码重复
- 与现有聊天功能无缝集成

**考虑的替代方案：**
- 创建新的独立组件：由于增加的复杂性和 UI 不一致而被拒绝

### 4. 文件搜索算法

**决策：** 实现带有优先级评分的模糊路径匹配

**理由：**
- 提供灵活的搜索功能
- 高效处理部分路径输入
- 优先考虑精确匹配和前缀匹配
- 对于大型文件列表保持良好性能

**考虑的替代方案：**
- 精确字符串匹配：由于用户体验差而被拒绝
- 全文搜索：由于复杂性和性能问题而被拒绝

## 风险 / 权衡

### 1. 性能风险

**风险：** 包含数千个文件的大型项目可能导致 API 响应缓慢

**缓解措施：**
- 实现深度限制（默认：5 级）
- 设置每个响应的最大文件数（默认：500）
- 使用服务器端缓存
- 为大型结果集实现分页

### 2. 安全风险

**风险：** 未授权访问文件系统路径

**缓解措施：**
- 在访问文件之前验证空间所有权
- 将文件系统访问限制在空间特定目录
- 为权限问题实现适当的错误处理

### 3. 浏览器兼容性风险

**风险：** 拖放功能在不同浏览器中可能表现不同

**缓解措施：**
- 使用标准 HTML5 拖放 API
- 在主要浏览器上进行测试
- 提供回退功能（手动选择）

### 4. 可扩展性风险

**风险：** 缓存可能会为大型项目消耗过多内存

**缓解措施：**
- 实现缓存大小限制
- 使用 LRU（最近最少使用）驱逐策略
- 在空间删除时清除缓存

## 迁移计划

1. **后端实现：**
   - 添加新的 API 端点
   - 实现缓存机制
   - 添加文件系统事件监控

2. **前端实现：**
   - 扩展 InputArea 组件
   - 实现 @ 提及 UI
   - 添加拖放支持

3. **测试：**
   - 使用不同项目大小测试 API 端点
   - 验证跨浏览器的前端功能
   - 测试边缘情况（大型项目、深层目录）

4. **部署：**
   - 部署后端更改
   - 部署前端更改
   - 监控性能指标
