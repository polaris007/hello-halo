## Context

当前 Halo 是一个 Electron 桌面应用，采用以下架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Electron 桌面应用                             │
├─────────────────────────────────────────────────────────────────┤
│  ┌─────────────┐         IPC          ┌───────────────────────┐ │
│  │  Renderer   │◄────────────────────►│    Main Process       │ │
│  │  (React)    │   contextBridge      │    (Node.js)          │ │
│  │             │                      │                       │ │
│  │  - UI 组件   │                      │  - Agent Loop         │ │
│  │  - Zustand  │                      │  - MCP Servers        │ │
│  │  - API 层   │                      │  - 文件操作            │ │
│  └─────────────┘                      │  - SQLite 数据库       │ │
│         │                             │  - HTTP Server        │ │
│         ▼                             └───────────────────────┘ │
│  ┌─────────────┘                              │                 │
│  │ Preload    │                               ▼                 │
│  └─────────────┘                      ┌───────────────┐        │
│                                       │  ~/.halo/     │        │
│                                       │  - halo.db    │        │
│                                       │  - spaces/    │        │
│                                       └───────────────┘        │
└─────────────────────────────────────────────────────────────────┘
```

现有优势：
- 已有 HTTP/WebSocket 服务器（`src/main/http/`）
- 已实现双传输层 API（IPC + HTTP）
- WebSocket 事件已与 IPC 事件对齐
- SQLite 已用于持久化存储
- 空间机制已成熟

## Goals / Non-Goals

**Goals:**

1. 将 Electron 桌面应用改造为 B/S 架构的 Web 应用
2. 保留所有核心功能：空间管理、对话、Agent 会话、MCP 支持、数字人
3. 实现用户认证（支持系统对接场景）
4. 实现多租户数据隔离：空间归属用户，不同用户的空间相互隔离
5. 移除对 Electron 的依赖
6. 所有文件操作在服务端执行
7. AI 提供商配置简化：配置文件或界面直接配置

**Non-Goals:**

1. 不保留 AI Browser 功能（依赖 Electron BrowserView）
2. 不保留产物展示功能
3. 不保留系统托盘、自动更新等桌面特有功能
4. 不改变核心业务逻辑（Agent Loop、MCP 协议等）
5. 不迁移到云端部署（仍为可自部署的单机服务）
6. 不保留第三方 AI 提供商认证（腾讯、千问、Kiro、Github 等）

## Decisions

### 1. 服务端框架选择：保留 Express

**决定**：继续使用现有的 Express 服务器作为 HTTP API 主入口

**理由**：
- 项目已有完整的 Express 服务器实现（`src/main/http/`）
- 现有路由已覆盖大部分 IPC 功能
- 避免引入新的框架学习成本

**替代方案**：
- Fastify：性能更好，但迁移成本高，收益不大
- NestJS：功能更全，但过度设计，不符合项目简洁风格

### 2. 前端构建工具：Vite

**决定**：将 electron-vite 改为纯 Vite 配置，输出 SPA

**理由**：
- 项目已使用 Vite，迁移成本低
- Vite 对 React SPA 支持良好
- 开发体验和构建性能优秀

### 3. 数据库：保留 SQLite

**决定**：继续使用 SQLite 作为数据库

**理由**：
- 项目定位为可自部署的单机服务，SQLite 足够
- 已有完整的数据库层实现
- 多用户隔离可通过 user_id 字段实现

**替代方案**：
- PostgreSQL：需要额外部署，增加用户负担
- 不推荐，除非明确需要分布式部署

### 4. 用户认证：可配置的 Token 认证

**决定**：使用 Token 认证机制，支持配置简化或绕过认证

**理由**：
- 项目定位为个人或小团队使用
- 需要支持系统对接场景（简化或绕过认证）
- 不需要复杂的 OAuth 集成

**实现**：
- 正常模式：用户登录获取 Token
- 系统对接模式：
  - 配置文件设置 `auth.mode: "disabled"` 完全禁用认证
  - 配置文件设置 `auth.mode: "simple"` 使用固定 Token
  - 配置文件设置 `auth.mode: "header"` 从请求头读取用户标识

### 5. 多租户数据隔离

**决定**：空间归属用户，通过 user_id 实现数据隔离

**理由**：
- 不同用户需要独立的操作空间
- 空间内的对话、文件等数据按用户隔离
- 通过数据库 user_id 字段和文件系统目录隔离实现

**实现**：
- 数据库层面：所有业务表添加 user_id 字段
- 文件系统层面：用户空间目录结构 `~/.halo/users/{user_id}/spaces/{space_id}/`
- API 层面：自动过滤当前用户的数据

### 6. AI 提供商配置：简化配置方式

**决定**：移除第三方认证，改为配置文件或界面直接配置

**理由**：
- 第三方认证（腾讯、千问、Kiro、Github 等）增加复杂度
- 用户可直接配置 API Key，更简单直接
- 配置文件方式便于部署和自动化

**实现**：
- 支持配置文件 `~/.halo/ai-sources.json` 配置 AI 提供商
- 支持界面直接添加/编辑 AI 提供商
- 配置格式：
  ```json
  {
    "providers": [
      {
        "id": "anthropic",
        "name": "Anthropic",
        "type": "anthropic",
        "apiKey": "sk-xxx",
        "baseUrl": "https://api.anthropic.com"
      },
      {
        "id": "openai",
        "name": "OpenAI",
        "type": "openai",
        "apiKey": "sk-xxx",
        "baseUrl": "https://api.openai.com"
      }
    ]
  }
  ```

### 7. 文件操作：服务端本地文件系统

**决定**：所有文件操作在服务端本地文件系统执行

**理由**：
- 空间目录在服务端，按用户隔离
- 不引入对象存储等复杂依赖
- 用户通过 Web 界面操作服务端文件

**影响**：
- 用户需要通过 Web 界面上传/下载文件
- 服务端需要有足够的存储空间

## Risks / Trade-offs

### Risk 1: 认证安全性

**风险**：简化认证可能带来安全风险

**缓解措施**：
- 默认启用认证
- 文档明确说明各认证模式的安全影响
- 系统对接模式下建议配合内网部署

### Risk 2: API Key 存储

**风险**：API Key 明文存储在配置文件中

**缓解措施**：
- 配置文件权限限制（仅当前用户可读）
- 支持环境变量配置 API Key
- 文档说明安全最佳实践

### Risk 3: 单点故障

**风险**：单机部署，服务挂掉则完全不可用

**缓解措施**：
- 提供健康检查端点
- 支持 PM2/Docker 等进程管理
- 文档说明高可用部署方案

### Risk 4: 文件上传限制

**风险**：通过 Web 上传大文件可能有性能问题

**缓解措施**：
- 设置合理的上传大小限制（如 100MB）
- 支持分片上传（后续优化）
- 文档说明服务端配置要求

### Risk 5: 数据迁移

**风险**：现有用户数据需要迁移

**缓解措施**：
- 提供迁移脚本，将 ~/.halo 数据迁移到新结构
- 数据库结构变化：添加 user_id 字段
- 为现有数据关联默认用户

## Migration Plan

### 阶段一：服务端重构

1. 创建独立的 `src/server/` 目录
2. 从 `src/main/` 提取服务层代码
3. 移除 Electron 相关依赖
4. 扩展 HTTP API，补充缺失的端点
5. 实现可配置的用户认证中间件
6. 移除第三方 AI 提供商认证代码

### 阶段二：多租户改造

1. 更新数据库 Schema，添加 user_id 字段
2. 实现用户数据隔离中间件
3. 更新文件系统目录结构
4. 提供数据迁移脚本

### 阶段三：前端改造

1. 移除 `src/preload/` 目录
2. 移除 IPC 相关代码
3. 修改 API 调用层，统一使用 HTTP
4. 更新 Vite 配置为纯 SPA
5. 添加登录页面（可配置禁用）
6. 更新 AI 提供商配置界面

### 阶段四：配置迁移

1. 更新配置文件格式
2. 提供 AI 提供商配置迁移脚本
3. 测试迁移流程

### 阶段五：部署配置

1. 提供 Docker 镜像
2. 提供独立可执行文件（pkg/nexe）
3. 编写部署文档

### 回滚策略

- 保留 Electron 分支
- 数据库 Schema 变更可逆（添加字段可删除）
