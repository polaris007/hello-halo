## Context

当前 Halo 是一个 Electron 桌面应用，采用以下架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Electron 桌面应用                             │
├─────────────────────────────────────────────────────────────────┤
│  ┌─────────────┐         IPC          ┌───────────────────────┐ │
│  │  Renderer   │◄────────────────────►│    Main Process       │ │
│  │  (React)    │   contextBridge      │    (Node.js)          │ │
│  │             │                      │                       │ │
│  │  - UI 组件   │                      │  - Agent Loop         │ │
│  │  - Zustand  │                      │  - MCP Servers        │ │
│  │  - API 层   │                      │  - 文件操作            │ │
│  └─────────────┘                      │  - SQLite 数据库       │ │
│         │                             │  - HTTP Server        │ │
│         ▼                             └───────────────────────┘ │
│  ┌─────────────┘                              │                 │
│  │ Preload    │                               ▼                 │
│  └─────────────┘                      ┌───────────────┐        │
│                                       │  ~/.halo/     │        │
│                                       │  - halo.db    │        │
│                                       │  - spaces/    │        │
│                                       └───────────────┘        │
└─────────────────────────────────────────────────────────────────┘
```

现有优势：
- 已有 HTTP/WebSocket 服务器（`src/main/http/`）
- 已实现双传输层 API（IPC + HTTP）
- WebSocket 事件已与 IPC 事件对齐
- SQLite 已用于持久化存储

## Goals / Non-Goals

**Goals:**

1. 将 Electron 桌面应用改造为 B/S 架构的 Web 应用
2. 保留所有核心功能：空间管理、对话、Agent 会话、MCP 支持、数字人
3. 实现用户认证和多用户数据隔离
4. 移除对 Electron 的依赖
5. 所有文件操作在服务端执行

**Non-Goals:**

1. 不保留 AI Browser 功能（依赖 Electron BrowserView）
2. 不保留产物展示功能
3. 不保留系统托盘、自动更新等桌面特有功能
4. 不改变核心业务逻辑（Agent Loop、MCP 协议等）
5. 不迁移到云端部署（仍为可自部署的单机服务）

## Decisions

### 1. 服务端框架选择：保留 Express

**决定**：继续使用现有的 Express 服务器作为 HTTP API 主入口

**理由**：
- 项目已有完整的 Express 服务器实现（`src/main/http/`）
- 现有路由已覆盖大部分 IPC 功能
- 避免引入新的框架学习成本

**替代方案**：
- Fastify：性能更好，但迁移成本高，收益不大
- NestJS：功能更全，但过度设计，不符合项目简洁风格

### 2. 前端构建工具：Vite

**决定**：将 electron-vite 改为纯 Vite 配置，输出 SPA

**理由**：
- 项目已使用 Vite，迁移成本低
- Vite 对 React SPA 支持良好
- 开发体验和构建性能优秀

### 3. 数据库：保留 SQLite

**决定**：继续使用 SQLite 作为数据库

**理由**：
- 项目定位为可自部署的单机服务，SQLite 足够
- 已有完整的数据库层实现
- 多用户隔离可通过 user_id 字段实现

**替代方案**：
- PostgreSQL：需要额外部署，增加用户负担
- 不推荐，除非明确需要分布式部署

### 4. 用户认证：简单 Token 认证

**决定**：使用简单的 Token 认证机制

**理由**：
- 项目定位为个人或小团队使用
- 不需要复杂的 OAuth 集成
- 首次启动时生成默认用户和 Token

**实现**：
- 服务端启动时检查是否有用户，无则创建默认用户
- 用户通过配置文件或命令行设置密码
- 支持多用户注册（可选功能）

### 5. 会话管理：内存 + 持久化

**决定**：活跃会话保存在内存，持久化到 SQLite

**理由**：
- 支持服务重启后会话恢复
- 内存访问快速，适合高频操作
- SQLite 持久化保证数据安全

### 6. 文件操作：服务端本地文件系统

**决定**：所有文件操作在服务端本地文件系统执行

**理由**：
- 保持现有行为，空间目录在服务端
- 不引入对象存储等复杂依赖
- 用户通过 Web 界面操作服务端文件

**影响**：
- 用户需要通过 Web 界面上传/下载文件
- 服务端需要有足够的存储空间

## Risks / Trade-offs

### Risk 1: 认证安全性

**风险**：简单 Token 认证可能不够安全

**缓解措施**：
- Token 随机生成，足够长度（32 字节）
- 支持 HTTPS（用户配置反向代理）
- Token 存储在服务端，不暴露给前端 URL

### Risk 2: 单点故障

**风险**：单机部署，服务挂掉则完全不可用

**缓解措施**：
- 提供健康检查端点
- 支持 PM2/Docker 等进程管理
- 文档说明高可用部署方案

### Risk 3: 文件上传限制

**风险**：通过 Web 上传大文件可能有性能问题

**缓解措施**：
- 设置合理的上传大小限制（如 100MB）
- 支持分片上传（后续优化）
- 文档说明服务端配置要求

### Risk 4: 数据迁移

**风险**：现有用户数据需要迁移

**缓解措施**：
- 提供迁移脚本，将 ~/.halo 数据迁移到新结构
- 数据库结构变化：添加 user_id 字段
- 兼容现有数据格式

## Migration Plan

### 阶段一：服务端重构

1. 创建独立的 `src/server/` 目录
2. 从 `src/main/` 提取服务层代码
3. 移除 Electron 相关依赖
4. 扩展 HTTP API，补充缺失的端点
5. 实现用户认证中间件

### 阶段二：前端改造

1. 移除 `src/preload/` 目录
2. 移除 IPC 相关代码
3. 修改 API 调用层，统一使用 HTTP
4. 更新 Vite 配置为纯 SPA
5. 添加登录页面

### 阶段三：数据迁移

1. 更新数据库 Schema，添加 user_id
2. 提供数据迁移脚本
3. 测试迁移流程

### 阶段四：部署配置

1. 提供 Docker 镜像
2. 提供独立可执行文件（pkg/nexe）
3. 编写部署文档

### 回滚策略

- 保留 Electron 分支
- 数据库 Schema 变更可逆（添加字段可删除）
