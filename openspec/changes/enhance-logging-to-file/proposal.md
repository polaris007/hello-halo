## Why

当前应用的server和client日志仅输出到控制台，不便于生产环境下的问题排查和监控。日志记录到文件可以提供持久化存储，便于后续分析和故障排查。特别是需要记录前后端报文内容以及与大模型交互的详细内容，这对调试API交互、追踪问题根源至关重要。

## What Changes

- **新增server日志文件记录功能**：将server端日志从仅控制台输出改为同时记录到文件
- **新增client日志文件记录功能**：将client端日志从仅控制台输出改为同时记录到文件
- **修改日志存储位置**：日志文件默认不存储在用户home目录下，而是放在应用启动目录的子目录中
- **新增报文内容日志**：在日志中记录前后端发送的报文内容
- **新增大模型交互日志**：在日志中记录发送给大模型的报文内容和返回内容
- **BREAKING**：日志目录默认位置变更，从`~/.halo/logs/`改为应用启动目录的`logs/`子目录

## Capabilities

### New Capabilities
- `structured-file-logging`: 结构化文件日志记录能力，支持server和client分别记录到不同文件
- `request-response-logging`: 报文内容日志记录能力，记录前后端通信的详细报文
- `ai-interaction-logging`: AI交互日志记录能力，记录与大模型交互的请求和响应

### Modified Capabilities
- `web-server`: 需要增强服务器的日志配置，支持文件日志记录和报文内容日志

## Impact

**影响的代码**：
- `src/server/utils/logger.ts`: 需要修改以支持应用启动目录的日志存储
- `src/server/index.ts`: 需要初始化server日志
- Client端代码（需要确定client日志实现位置）
- API路由处理器：需要添加报文内容日志记录
- AI交互层：需要添加大模型交互日志记录

**依赖**：
- Node.js文件系统模块（已有）
- 可能需要日志轮转库（如`winston`或`pino`）

**配置变更**：
- 新增环境变量支持自定义日志目录：`HALO_LOG_DIR`
- 新增配置选项控制日志级别和内容详略程度

**数据存储**：
- 日志文件存储在应用启动目录的`logs/`子目录下
- 可能产生较大的日志文件，需要考虑日志轮转策略

**向后兼容性**：
- 默认日志位置变更可能影响现有部署的日志收集配置
- 建议提供配置选项支持恢复旧的日志位置
